# Phase 0 research

Findings that the design relies on, with how each one was obtained. Run date: 2026-10-20. fdroidserver version used: **2.4.5** from PyPI, unless stated otherwise.

Test APKs were built with [`tools/fixtures/make_apk.py`](../../tools/fixtures/make_apk.py): code-free APKs with a chosen package, version, label, icon and signing key. fdroidserver indexes them like any other APK.

## 1. Installation on the tier 1 distributions

Method: fresh official container images, then exactly what the installer will do: install distribution packages, create a Python virtual environment, `pip install fdroidserver==2.4.5`, `fdroid init --no-prompt` in an empty directory, copy one APK into `repo/`, `fdroid update -c`.

| Distribution | Python | fdroidserver package | apksigner | default JDK | Caddy package | Managed install result |
| --- | --- | --- | --- | --- | --- | --- |
| Debian 12 | 3.11.2 | 2.2.1 | 31.0.2 | 17 | 2.6.2 | works |
| Debian 13 | 3.13.5 | 2.4.2 | 35.0.2 | 21 | 2.6.2 | works |
| Ubuntu 22.04 | 3.10.12 | 2.1 | 31.0.2 | 11 (17 and 21 available) | not packaged | works |
| Ubuntu 24.04 | 3.12.3 | 2.2.1 | 31.0.2 | 21 | 2.6.2 | works |

Packages needed, and sufficient, on all four: `python3`, `python3-venv`, `default-jdk-headless`, `apksigner`, `git`, `ca-certificates`. No Android SDK.

Findings:

* **`git` is mandatory.** Without the `git` binary, every `fdroid` command (even `fdroid --version`) fails at import time because fdroidserver imports GitPython. The installer must install it.
* Only Debian 13 ships a fdroidserver recent enough for the 2.4.0 minimum. On the three others the managed install is required, which confirms it as the default.
* `fdroid init --no-prompt` succeeds without an Android SDK. It writes `sdk_path: /usr/lib/android-sdk` because the `apksigner` package installs there; harmless.
* Caddy is not packaged in Ubuntu 22.04: the standalone HTTPS option needs Caddy's official APT repository there (or everywhere, for a current version).
* Not verified: arm64 (no arm64 runner available during this research), Tier 2 distributions.

## 2. `fdroid init`

* Creates `config.yml` (mode 600) and `keystore.p12` (mode 600), and `repo/`.
* **Writes `keystorepass` and `keypass` in clear text in `config.yml`.** For repositories it creates, the panel must move them to its secrets file and replace them by `{env: ...}` references right after `init`.
* The key alias defaults to the host name (`repo_keyalias: localhost` in a container) and the distinguished name to `CN=<hostname>, OU=F-Droid`. The panel passes `--repo-keyalias` and `--distinguished-name` explicitly.
* No `repo_url`, `repo_name` or `repo_icon` is set; the panel's creation wizard must set them.

## 3. `fdroid update --create-metadata`

* On a new app it writes a skeleton `metadata/<appid>.yml` with surprising defaults: `Categories` set to the **name of the repository directory**, `CurrentVersionCode: 2147483647`, empty strings for author, links and summary. The panel therefore **writes the metadata file itself** when an app is added, and does not rely on `-c`.
* On an app that already has a metadata file, the file is left **byte for byte unchanged**, comments included.
* When `repo_icon` does not exist, `fdroid update` generates a placeholder icon and warns. The panel's creation wizard provides an icon.

## 4. APK signed by a different key

* Without any pinning, `fdroid update` **accepts and publishes** a new version of an existing app signed by a different key, without even a warning. The index then lists versions with two different signers. This confirms the blocking check of the upload pipeline (ARCHITECTURE 8.3).
* fdroidserver supports a per app metadata field **`AllowedAPKSigningKeys`** (SHA-256 of the signing certificate). With it, an APK signed by another key is **left out of the index**, with only a `WARNING` line in the log, and the run still succeeds.
* Consequences:
  * the panel writes `AllowedAPKSigningKeys` when an app is first added, so the protection also holds for anyone using the command line on the same repository;
  * after every publish the panel compares the APK files present in `repo/` with the versions actually in the index, and reports any APK that was left out, with the reason taken from the log.

## 5. Locking

fdroidserver takes **no lock** of its own (no `flock`, no lock file). `repo/status/running.json` is a status report written during and after a run, not a lock. The panel's per repository lock protects the panel's own jobs only; the documentation tells users not to run `fdroid` by hand on a repository while the panel publishes it.

## 6. Editing YAML without damaging hand written files

Compared on a hand written metadata file (comments, inline comments, a multi line description) and on the `config.yml` generated by `fdroid init`:

* `fdroid rewritemeta` **removes all comments**, adds fields (`AutoUpdateMode`, `UpdateCheckMode`) and blank lines. The panel never uses it to write files.
* `ruamel.yaml` in round-trip mode keeps comments, inline comments, key order and block scalars. With `indent(mapping=2, sequence=4, offset=2)` and a large `width`, its output follows fdroidserver's canonical style, so the only changes are the edited value and, for files indented differently by hand, a re-indentation to that canonical style.
* The leading `---` of `config.yml` is dropped unless `explicit_start` is set. The panel detects it and keeps it.
* Round trip of the generated `config.yml` (about 400 lines, mostly comments): identical apart from the `---` above.

## 7. Localized texts

Tested with the `localized` and `hand-written` fixtures (`tools/fixtures/`):

* Texts in `metadata/<appid>/<locale>/` (`name.txt`, `summary.txt`, `description.txt`) are published per locale, and graphics and screenshots in `metadata/<appid>/<locale>/images/` are copied to `repo/<appid>/<locale>/`.
* **When `Name`, `Summary` or `Description` is set in `metadata/<appid>.yml`, it replaces that field for every locale**: the `fr-FR` name disappears from the index as soon as `Name:` exists in the YAML file. Consequence: the panel stores app texts only in the locale files. When it imports an app whose texts are in the YAML file, it shows them as the default language text and, on the first edit in another language, moves them to the default locale files so translations become visible.
* Names and summaries are stripped of surrounding whitespace; descriptions are published exactly as written, trailing newline included. The panel writes `description.txt` without a trailing newline.

## 8. Index files

Produced by `fdroid update` 2.4.5 for a repository with one APK: `entry.jar`, `entry.json`, `index-v1.jar`, `index-v1.json`, `index-v2.json`, `index.jar`, `index.xml`, `index.html`, `index.css`, `index.png`, icons in `icons/` and `icons-120` to `icons-640`, and `status/`. These are the files the panel serves and backs up before each publish.
